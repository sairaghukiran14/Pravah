Defects found during this pass

All three are fixed and covered by tests. Two were introduced by my own earlier work.

Fixed

The test suite was making live, billable Sarvam calls

Importing almost anything in src pulls in Prisma, and the Prisma client loads .env as an import side effect. That put the real SARVAM_API_KEY into process.env, so any test touching a transcribe, translate or speak node hit the paid API — on every npm test and every CI run, against production quota.

BARE: 0 AFTER_PRISMA: 36

Caught because a new integration test failed with a genuine Sarvam 400 carrying a real request_id. Fixed with a vitest.setup.ts that forces the mock key before every test file; tests that want the HTTP layer now set their own key and stub fetch explicitly.

Fixed

Audio size limit disagreed with itself

Raising the transcription ceiling to 50MB left api/audio/upload reading the same environment variable with a fallback of 10. With the variable unset, uploads rejected at 10MB (~5.5 min) while transcription believed it allowed 27 minutes — the stricter gate won silently, so most of the chunking work was unreachable and the symptom looked like an unrelated upload bug.

Both now read one exported constant, the same way STT_MAX_SECONDS is shared between the executor and the biller.

Fixed

A test passed for the wrong reason

The assertion that an unsplittable WebM produces an actionable error was satisfied by a fallback in executeSarvamSTT that replaces any buffer under 100 bytes with 1.5 seconds of silence — resetting the extension to wav. The test never exercised the WebM path. Rewritten with a 4KB buffer; it now genuinely asserts (webm).

What the new integration tests prove

The unit tests priced a duration correctly. They could not show the number ever reaches pricing.

  • Chunked transcription really chunks. A 95s recording issues exactly 4 upstream requests, each a valid standalone WAV within the 30s limit, cut on frame boundaries, with no audio dropped between segments — and the transcripts rejoin in order.
  • Billing units survive the graph. durationSeconds set on a run input reaches the STT node's price through audio_input and an edge: 25s → ₹0.375, 95s → ₹1.50, 300s → ₹3.75. Page count does the same through document_input: a 10-page PDF bills ₹7.50 against Sarvam's ₹5.00.
  • The hold always covers the settlement. Asserted across every configurable podcast length, so a node cannot spend more credit than was reserved for it.
  • Errors degrade correctly. Provider failures pass through unchanged; only the duration case is rewritten into guidance.

Open issues

Found and confirmed, not fixed — each needs a decision rather than a patch.

Open

Translate breaks before the audio does

STT now handles a 20-minute recording, but MAX_TEXT_LENGTH caps translate and TTS at 5,000 characters — roughly 6–7 minutes of speech. The Coimbatore pipeline therefore survives a 30-second demo and a 5-minute consultation, then fails on a long one at a node the user would not expect. The failure dialog explains it and suggests a Summarize node, but the real fix is chunking translate the way STT was chunked.

Open

Correct pricing now exceeds the credit hold

A run reserves a flat 10 credits. With per-page and per-turn pricing, a 40-page OCR projects ₹30 and a 20-turn podcast ₹18.50 — both above the hold, so those runs are skipped with "Run budget exhausted" instead of executing. Arithmetically right, but work that used to run at a loss now will not start. RUN_RESERVATION_CREDITS is configurable; ~50 restores them at honest prices.

Open

A 50MB upload cannot reach a Vercel deployment

Audio uploads go to /api/audio/upload as multipart form data, and Vercel caps request bodies at about 4.5MB regardless of our own limit. At 16kHz mono WAV (32KB/s) that is roughly 2 minutes 20 seconds of audio. Everything longer works locally and fails in production. Long recordings need a presigned upload straight to R2, bypassing the function.

Open

Failed nodes discard the input that caused them

The catch in executeSingleNode returns input: { text }, dropping the payload. Billing is unaffected — failed nodes are never charged — but the stored NodeRun row loses the one thing needed to reproduce the failure.

Open

Unreadable audio is silently replaced with silence

executeSarvamSTT substitutes 1.5 seconds of generated silence for any buffer under 100 bytes. The user gets a confident transcript of nothing instead of a clear failure — and it is what made the WebM test above pass for the wrong reason.

Open

The app is still not deployed

Unchanged from earlier: every URL points at localhost:3000, and the Google OAuth consent screen has not been confirmed as production. None of this session's work reaches a user until those two clear.

Suggested order

  • Before anything else — rotate the Sarvam API key. It sat in an environment where the test suite could spend it, and any CI run that executed the suite used real quota.
  • Then — deploy, and confirm the OAuth consent screen reads "In production".
  • Then — raise RUN_RESERVATION_CREDITS, so correctly-priced OCR and podcast runs can start.
  • Before promoting long audio — presigned R2 upload and translate chunking. Until both land, the honest ceiling is about two minutes of audio in production.
